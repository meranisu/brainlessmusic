**Auth (JWT + bcrypt):** Built and manually verified end-to-end.
- `POST /auth/register` — accepts `{ username, password }`, hashes with bcrypt (12 salt rounds), inserts into `users`. Returns `201 { id, username, isAdmin }`; `409` on duplicate username, `400` on missing fields or a password under 8 characters / a username outside `[A-Za-z0-9._-]{2,32}`. **Gating is configurable as of 2026-09-09**: `ALLOW_OPEN_REGISTRATION` (default `true`) lets anyone create a listener account; `false` requires an admin's token. Either way the first account on an empty server is allowed through and becomes an admin. Self-serve accounts are never admins.
- `POST /auth/login` — verifies bcrypt hash, returns `200 { token }` (JWT, `sub`+`username` payload, expiry from `JWT_EXPIRES_IN` env, default `7d`) or `401` on bad credentials.
- `GET /auth/me` — protected via `fastify.authenticate` decorator (`src/plugins/auth.ts`); requires `Authorization: Bearer <token>`, returns `200 { id, username }` (never the password hash), `401` if the header is missing/malformed or the token is invalid/expired.
- JWT secret read from `.env`'s `JWT_SECRET`. Since 2026-09-09 the server **refuses to boot** if it is the default, empty, or under 32 characters, unless `NODE_ENV` is `development` or `test` (`utils/secretPolicy.ts`); `config.jwtSecret` still falls back to `'change-me'` so the CLI scripts keep working.
- Verified manually via curl: register → duplicate/missing-field rejection → login success/failure (wrong password, unknown user) → `/auth/me` with no token, malformed header, garbage token, and a valid token. All returned the expected status codes; test user removed afterward.
- New deps: `bcrypt`, `jsonwebtoken` (+ `@types/*`). Note: `bcrypt`'s build-time dependency `@mapbox/node-pre-gyp` pulls a vulnerable `tar` version (`npm audit`: 1 high, 1 critical) — install-time only, not part of the runtime request path, but worth a look if this ships to a shared/CI environment.

- Schema (migration `0002_create_library.sql`): `artists` (id, name unique, created_at), `albums` (id, title, artist_id FK, year, created_at, unique on title+artist_id), `tracks` (id, path unique, title, artist_id FK, album_id FK, track_number, duration, format, file_size, date_added). **Audio streaming:** Built and manually verified end-to-end.
- `GET /tracks/:id/stream` (`src/routes/tracks.ts`) — requires auth (`fastify.authenticate`); looks up the track by id, `fs.stat`s its stored path, and streams the file back with `Content-Type` set from file extension (`src/services/streaming.ts`: `.flac`→`audio/flac`, `.opus`→`audio/opus`, `.mp3`→`audio/mpeg`, `.m4a`→`audio/mp4`, `.ogg`→`audio/ogg`; unknown falls back to `application/octet-stream`).
- Byte-range support: parses a single `Range: bytes=...` header (start-end, open-ended, and suffix forms), responds `206` with `Content-Range`/`Content-Length`/`Accept-Ranges: bytes`; malformed or out-of-bounds ranges get `416` with `Content-Range: bytes */<size>`. No request-range header falls through to a full `200` response. Multipart (multi-range) requests aren't supported — treated as invalid.
- Transcoding: `?quality=low` streams the file through `fluent-ffmpeg` on the fly (`libopus`, 64k target bitrate, ogg container, `Content-Type: audio/ogg`, `Accept-Ranges: none` — output length is unknown ahead of time so range serving doesn't apply to this path). `.noVideo()` is required on the ffmpeg command — without it, ffmpeg transcodes embedded cover-art image streams into a spurious Theora video track, bloating the output.
- Errors: unknown/non-numeric id → `404`; DB row present but file missing from disk → `500` with a clear JSON message (`{ error, trackId }`), full error logged server-side via `request.log.error`; no/invalid bearer token → `401` (existing `fastify.authenticate` decorator).
- New dep: `fluent-ffmpeg` (+ `@types/fluent-ffmpeg`). Requires system `ffmpeg`/`ffprobe` on `PATH` (already present in this WSL2 dev environment; not yet containerized for deployment).
- Verified manually against the real library (19 Opus tracks) via curl against a running dev server + temp auth user (removed after): full-file GET matched the DB `file_size` exactly and decoded cleanly; a mid-file range request (`bytes=1000000-1099999`) returned `206` with correct headers and bytes that `cmp` confirmed byte-identical to the same slice of the source file on disk; open-ended and suffix range forms both resolved to the same correct tail bytes; out-of-bounds and start>end ranges both returned `416`; a track id with no DB row returned `404`; a temporarily-inserted DB row pointing at a nonexistent path returned `500` with the file path logged; `?quality=low` produced a smaller (~2.62 MB vs ~4.00 MB original), valid, cleanly-decoding Opus/Ogg stream at the requested track's length. Test track row and test user cleaned up afterward.

**Playlists:** Built and manually verified end-to-end.
- Schema (migration `0003_create_playlists.sql`): `playlists` (id, name, owner_id FK → users, created_at), `playlist_tracks` (playlist_id, track_id, position, added_at — composite PK on `(playlist_id, track_id)` so a track can't be added twice to the same playlist, but the same track can sit in many different playlists). Indexes on `playlists.owner_id`, `playlist_tracks.playlist_id`, `playlist_tracks.track_id`.
- All routes (`src/routes/playlists.ts`) require auth (`fastify.authenticate`). Ownership is enforced by a single shared helper (`loadOwnedPlaylist` in that file) used on every route that takes a playlist id — 404 if the playlist doesn't exist, 403 if it exists but belongs to a different user, so the check can't be accidentally skipped on one route.
- `POST /playlists` — `{ name }`, owned by the logged-in user; `400` on missing/blank name. `GET /playlists` — the caller's own playlists only (`id`, `name`, `trackCount`, `createdAt`). `GET /playlists/:id` — detail with tracks in position order (title/artist/album/duration/format/position). `PATCH /playlists/:id` — rename, `{ name }`. `DELETE /playlists/:id` — deletes the playlist and its `playlist_tracks` rows in one transaction (no FK-cascade relied on — `better-sqlite3` enables `foreign_keys` enforcement by default per connection, none of this project's FKs cascade, so cleanup is explicit in `src/db/playlists.ts`; corrected 2026-09-03, this previously said enforcement was off — see `.docs/reference/database-schema.md`).
- `POST /playlists/:id/tracks` — `{ trackId }`, appends at `MAX(position)+1` (or `0` for an empty playlist); `404` if the track doesn't exist in the library, `409` if it's already in the playlist. `DELETE /playlists/:id/tracks/:trackId` — `404` if the track isn't in the playlist.
- `PATCH /playlists/:id/tracks/reorder` — body is a full ordered list, `{ trackIds: [...] }`; the server verifies it's exactly the playlist's current track set (same ids, no dupes/missing/extra) before applying, `400` otherwise — this was simpler to make provably correct than a single `{ trackId, newPosition }` move, and playlists are small enough that shipping the whole order each time is cheap.

**Track upload:** Built and manually verified end-to-end.
- `POST /tracks/upload` (`src/routes/tracks.ts`, requires auth) — `multipart/form-data`, single `file` field, via `@fastify/multipart` (registered in `src/app.ts` with `limits.fileSize` from `MAX_UPLOAD_SIZE_MB`, default 100, and `limits.files: 1`).
- Extension allow-list is shared with the scanner (`AUDIO_EXTENSIONS` in the new `src/services/trackTags.ts`: `.flac`/`.opus`/`.mp3`/`.m4a`/`.ogg`) — unsupported extensions get `400` before anything is written to disk.
- The client-supplied filename is never trusted beyond its extension: the file is streamed to `UPLOAD_STAGING_PATH` (default `./data/upload-staging`, gitignored under `data/`) under a server-generated `crypto.randomUUID()` name. Oversized uploads (over the configured limit) are caught via `@fastify/multipart`'s `file.truncated` flag after streaming completes, the partial staged file is deleted, and the response is `413`.
- Tag extraction was pulled out of `src/services/scanner.ts` into a shared `extractTrackTags()` (`src/services/trackTags.ts`) so scan and upload apply identical fallback rules (missing title → filename, missing artist → "Unknown Artist") — the upload path passes the *original* client filename for this fallback, not the random staging name. Corrupt/unparseable files are rejected with `400` and the staged file is deleted (never filed into the library) — same music-metadata leniency as the scanner otherwise (e.g. a plain-text file renamed to `.mp3` doesn't always throw; that mirrors existing scan behavior, not a gap specific to upload).
- Filing (`src/services/trackFiling.ts`, new) computes `LIBRARY_PATH/<Artist>/<Album>/<filename>` — artist/album folder names sanitized (invalid filesystem characters replaced, trailing dots stripped, empty names fall back to "Unknown Artist"/"Unknown Album"), filename prefers the sanitized original upload name and falls back to the sanitized title only if that's empty. Never overwrites an existing file — same-name collisions get a `(2)`, `(3)`, ... suffix. Staged file is moved (not copied) into place via `fs.rename`, with an `EXDEV` (cross-filesystem) fallback to copy+delete so staging and the library directory don't have to share a mount.
- DB insert reuses the existing `upsertTrack()` (`src/db/library.ts`) unchanged — same idempotent insert/update-by-path logic as a rescan, so re-running `/library/scan` after an upload updates the same row rather than duplicating it. Response is `201 { track }` using the same lean shape as `GET /tracks` (new `getTrackSummaryById()` in `src/db/browse.ts`), so the client doesn't need a follow-up fetch to confirm what was added.
- New dep: `@fastify/multipart`.
- Verified manually against the real library/DB (backend running via `npm run dev`, real `LIBRARY_PATH`) with a temp registered/logged-in user (removed after): uploaded a tagged MP3, an untagged Opus (confirmed filename/"Unknown Artist" fallback), and a tagged FLAC — all landed at the correct `Artist/Album/filename` path and appeared correctly tagged in the DB; a corrupt FLAC (bad magic bytes) was rejected `400` with no file left in staging or the library; a `.txt` file was rejected `400`; an unauthenticated request got `401`; a path-traversal filename (`../../../../etc/passwd_style../../file.mp3`) was sanitized down to `file.mp3` and stayed inside the intended `Artist/Album/` folder, not written outside `LIBRARY_PATH`; an oversized upload against a temporary low-limit (`MAX_UPLOAD_SIZE_MB=1`) instance of the server got `413` with the partial file cleaned from staging; re-running `POST /library/scan` afterward reported all uploaded files as updates (not additions) with no change in total track count, confirming no duplication. **Smart shuffle:** Built and manually verified end-to-end (see `.docs/features/smart-shuffle/planning.md`).
- Only the "avoid same artist back-to-back" shuffle needs the backend — plain shuffle/repeat-one/repeat-all are pure client-side queue operations with no server involvement (tracked as a follow-up for the Android playback plan, not built here).
- `smartShuffle()` (new `src/services/shuffle.ts`) — pure function, no DB/HTTP dependency: groups `{ trackId, artistId }` by artist, then greedily interleaves by always placing next from the largest remaining artist group that isn't the one just placed (the standard "reorganize string" algorithm). Guarantees zero adjacent same-artist pairs unless one artist exceeds half the set, in which case it hits the mathematical minimum (`2×dominant - total - 1`) rather than leaving it to chance. Input is pre-shuffled so both within-group order and equal-size-group tie-breaks vary between calls. `artist_id IS NULL` tracks are grouped together as their own bucket, not scattered as singletons.
- `POST /shuffle` (`src/routes/shuffle.ts`, requires auth, same as browsing — no per-track ownership model exists in this API for any endpoint) — body `{ trackIds: number[] }` (same convention as the playlist reorder endpoint), response `{ tracks: [...] }` reusing the existing lean track-summary shape via a new batch lookup (`getTrackSummariesByIds()` in `src/db/browse.ts`) and a matching batch `findTracksByIds()` in `src/db/library.ts` — both single `IN (...)` queries, not N+1. `400` on empty/missing/non-integer `trackIds`, `404` with `{ missing: [...] }` on any unknown track id, `401` unauthenticated.
- New unit test suite (`src/services/shuffle.test.ts`, run via Node's built-in test runner — `npm test`, first test infra in this repo, no new dependency) covering balanced/skewed/single-artist/null-artist/empty-input cases and exact-minimum-violation math, since some of these (e.g. a controlled 10-vs-2 artist split) aren't practical to construct from the real library alone.
- Verified manually against the real library (20 tracks: 19 from one artist + 1 uploaded-test-data track from a different artist) with a temp registered/logged-in user (removed after): shuffling the full library correctly isolated the single minority track as the one adjacency break, hitting the exact theoretical minimum (17 forced same-artist pairs); a single-artist-only subset returned a valid randomized order without erroring; three repeated identical requests each returned a different track ordering; empty `trackIds` and missing body both returned `400`, an unknown track id returned `404` listing it, no bearer token returned `401`.
