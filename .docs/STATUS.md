**Auth (JWT + bcrypt):** Built and manually verified end-to-end.
- `POST /auth/register` — accepts `{ username, password }`, hashes with bcrypt (12 salt rounds), inserts into `users`. Returns `201 { id, username, isAdmin }`; `409` on duplicate username, `400` on missing fields or a password under 8 characters / a username outside `[A-Za-z0-9._-]{2,32}`. **Gating is configurable as of 2026-09-09**: `ALLOW_OPEN_REGISTRATION` (default `true`) lets anyone create a listener account; `false` requires an admin's token. Either way the first account on an empty server is allowed through and becomes an admin. Self-serve accounts are never admins.
- `POST /auth/login` — verifies bcrypt hash, returns `200 { token }` (JWT, `sub`+`username` payload, expiry from `JWT_EXPIRES_IN` env, default `7d`) or `401` on bad credentials.
- `GET /auth/me` — protected via `fastify.authenticate` decorator (`src/plugins/auth.ts`); requires `Authorization: Bearer <token>`, returns `200 { id, username }` (never the password hash), `401` if the header is missing/malformed or the token is invalid/expired.
- JWT secret read from `.env`'s `JWT_SECRET`. Since 2026-09-09 the server **refuses to boot** if it is the default, empty, or under 32 characters, unless `NODE_ENV` is `development` or `test` (`utils/secretPolicy.ts`); `config.jwtSecret` still falls back to `'change-me'` so the CLI scripts keep working.

**Audio streaming:** Built and manually verified end-to-end.
- `GET /tracks/:id/stream` (`src/routes/tracks.ts`) — requires auth (`fastify.authenticate`); looks up the track by id, `fs.stat`s its stored path, and streams the file back with `Content-Type` set from file extension (`src/services/streaming.ts`: `.flac`→`audio/flac`, `.opus`→`audio/opus`, `.mp3`→`audio/mpeg`, `.m4a`→`audio/mp4`, `.ogg`→`audio/ogg`; unknown falls back to `application/octet-stream`).
- Byte-range support: parses a single `Range: bytes=...` header (start-end, open-ended, and suffix forms), responds `206` with `Content-Range`/`Content-Length`/`Accept-Ranges: bytes`; malformed or out-of-bounds ranges get `416` with `Content-Range: bytes */<size>`. No request-range header falls through to a full `200` response. Multipart (multi-range) requests aren't supported — treated as invalid.
- **Caching (2026-09-10):** the direct path sends a strong `ETag` (size + mtime), `Last-Modified`, and `Cache-Control: private, max-age=86400`, and answers `304` to `If-None-Match` / `If-Modified-Since` under RFC 9110 precedence — a tag decides alone, the date is consulted only in its absence and compared at whole seconds. `If-Range` is honoured: a range whose validator no longer matches is dropped and the whole file resent, since splicing new bytes onto old ones is a corrupt stream that arrives looking like a successful `206`. The tag is **strong** on purpose — a weak one may not validate an `If-Range`, which would have silently killed resumable seeking. A day rather than a week bounds how long a replaced file can keep serving the old rip; the media token in the URL rotates every two hours anyway, so a longer window buys little.
- ~~Transcoding (superseded 2026-09-10 by "Converted copies are cached" below — `?quality=low` is now a cached file, not a live encode):~~ `?quality=low` streams the file through `fluent-ffmpeg` on the fly (`libopus`, 64k target bitrate, ogg container, `Content-Type: audio/ogg`, `Accept-Ranges: none` — output length is unknown ahead of time so range serving doesn't apply to this path, and it sends `Cache-Control: no-store` for the same reason). `.noVideo()` is required on the ffmpeg command — without it, ffmpeg transcodes embedded cover-art image streams into a spurious Theora video track, bloating the output.
- **Converted copies are cached (2026-09-10):** `?quality=low` writes the conversion to disk and serves the file, so the data-saver path now has `Content-Length`, byte ranges, an `ETag`, `304`s and a working scrubber — it had none of those as a live encode. Measured on a 25s FLAC: 0.88s cold, 0.027s warm, 3.32 MB down to 0.24 MB (93%). Converting is skipped when the source is under 1.5x the 64k target. Raw `.aac` is remuxed to `.m4a` on every path, because ADTS reports a duration ~50% long to both ffprobe and Chrome. `TRANSCODE_PATH`, `TRANSCODE_CACHE_MAX_MB` (2048, LRU, evicted after a write), `TRANSCODE_MIN_SOURCE_BITRATE_RATIO`. The live-transcode path and its `?t=` offset were removed as unreachable once a finished file could be seeked by byte range.
- **Resume where you left off (2026-09-10):** `playback_state` holds one row per user — `user_id` is the primary key, so last-write-wins is a schema property rather than a rule application code has to remember. Per-device state was considered and rejected: the desktop would never learn where the phone got to. The current track is **not** a column; it is `queue[queue_index]`, so there is only one place to be right. `GET/PUT/DELETE /api/me/playback-state`, all auth-scoped to the caller. The load path is where the judgement is: tracks deleted or flagged `missing_since` are filtered out on read (the same rule browse uses), the saved index is re-derived from the survivors rather than reused, and if the played track itself is gone the resume moves *forward* to the next survivor at position 0 rather than back to the queue's start. `null` when nothing playable remains. The client writes every 10 s while playing, on pause, on track change, and on `visibilitychange` — not `beforeunload`, which does not fire reliably on a phone. **It restores paused on purpose:** browsers block autoplay without a gesture, so "resume and play" would silently do nothing on a phone; Android has no such limit and may decide differently (Q9). **Closing the player forgets, logging out does not** — `stop` and `stopAndForget` are separate so an expiring token cannot throw away the position.
- **Data saver is reachable (2026-09-10):** the web player has a toggle on both surfaces — a pill in the phone sheet beside shuffle and repeat, a button on the desktop bar. It applies to the track already playing rather than the next one, carrying the position, the play/pause state and the in-progress scrobble across the swap; that is only possible because the converted copy is a finished file that can be seeked. The preference is per-device (`localStorage`, key `brainlessmusic.dataSaver`), not per-account, since the phone on mobile data and the desktop on the LAN share a login and want different answers. Alongside it a readout shows **what was served, not what was asked for** — `variantFor` declines to downgrade a source already at or below the target, so those two come apart on exactly the files the rule protects. An `<audio>` element exposes no response headers, so this costs one `Range: bytes=0-0` request per track; on a cold cache it is nearly free, because the element is fetching the same variant and the in-flight map collapses them. Measured on the real library: 115 kbps Opus serves at **65 kbps**, a 44% saving. The encoder was corrected the same day ([A12](QUESTIONS.md)): libopus read `-b:a 64k` as a VBR target and ran 16% over it, so `-vbr constrained` was added and the variant id bumped `opus64` → `opus64c`, since the id *is* the cache key and old entries would otherwise keep serving the previous encode. 1,597,894 → 1,395,366 bytes on the same source.
- **Seven formats (2026-09-10):** the library accepts `.flac`, `.opus`, `.mp3`, `.m4a`, `.ogg`, `.wav` and `.aac`. All seven verified against real ffmpeg fixtures for tags, duration and waveform decode, and FLAC/WAV/AAC all confirmed playing in headless Chromium. **Raw `.aac` is a known trap:** frame-scanning gives the true duration but ffprobe and Chrome both estimate ~50% long from bitrate, so the seek bar lies — roadmap box 24 remuxes it to `.m4a`. `MAX_UPLOAD_SIZE_MB` was raised from 100 to **1024** the same day, since a single hi-res FLAC exceeds the old ceiling; the route is admin-only, the web client uploads 3 at a time (so staging can hold ~3× that), and a future reverse proxy needs its own body limit raised to match.
- **Seeking the data-saver path (2026-09-10) — SUPERSEDED the same day.** `?t=` was removed in `216aaf7`: once a converted copy is a finished file on disk, seeking is an ordinary byte range and the offset had no caller. The UI gap this entry named is closed too — see "Data saver is reachable" below. Kept for the record: `?t=<seconds>` started the transcode at an offset, applied as an ffmpeg *input* seek so it jumps rather than decodes-and-discards. Byte ranges still do not apply to a live encode — this is the way back into the middle of a track on that path. Invalid offsets are `400`, not clamped. Verified byte-identical against a locally-seeked reference. **No UI yet:** there is no data-saver toggle in the web player, and the client must add the offset to `audio.currentTime` itself — both are Phase 3 of `.docs/features/formats-and-transcoding/planning.md`.
- **Transcode lifecycle (2026-09-10) — the API named here no longer exists;** `transcodeToLowQuality` and `TranscodeSession` went with the live path in `216aaf7`. The bug it records is still worth knowing, since any future live path would hit it again: `transcodeToLowQuality` returned a `TranscodeSession` (`{ stream, stop }`) and the route calls `stop()` on response close. Previously the ffmpeg handle was discarded, so a skipped track left ffmpeg blocked on a full pipe for the life of the server — one stranded process per skip. The kill is re-issued on ffmpeg's `start` event if a stop landed before the process existed, which is the window a fast skip actually hits.

The full-quality path is unaffected. `activeTranscodes` appears in the health snapshot and on the diagnostics page.

**Playlists:** Built and manually verified end-to-end.
- Schema (migration `0003_create_playlists.sql`): `playlists` (id, name, owner_id FK → users, created_at), `playlist_tracks` (playlist_id, track_id, position, added_at — composite PK on `(playlist_id, track_id)` so a track can't be added twice to the same playlist, but the same track can sit in many different playlists). Indexes on `playlists.owner_id`, `playlist_tracks.playlist_id`, `playlist_tracks.track_id`.
- All routes (`src/routes/playlists.ts`) require auth (`fastify.authenticate`). Ownership is enforced by a single shared helper (`loadOwnedPlaylist` in that file) used on every route that takes a playlist id — 404 if the playlist doesn't exist, 403 if it exists but belongs to a different user, so the check can't be accidentally skipped on one route.

**Track upload:** Built and manually verified end-to-end.
- `POST /tracks/upload` (`src/routes/tracks.ts`, requires auth) — `multipart/form-data`, single `file` field, via `@fastify/multipart` (registered in `src/app.ts` with `limits.fileSize` from `MAX_UPLOAD_SIZE_MB`, default 100, and `limits.files: 1`).
- Extension allow-list is shared with the scanner (`AUDIO_EXTENSIONS` in the new `src/services/trackTags.ts`: `.flac`/`.opus`/`.mp3`/`.m4a`/`.ogg`) — unsupported extensions get `400` before anything is written to disk.
- The client-supplied filename is never trusted beyond its extension: the file is streamed to `UPLOAD_STAGING_PATH` (default `./data/upload-staging`, gitignored under `data/`) under a server-generated `crypto.randomUUID()` name. Oversized uploads (over the configured limit) are caught via `@fastify/multipart`'s `file.truncated` flag after streaming completes, the partial staged file is deleted, and the response is `413`.
- Tag extraction was pulled out of `src/services/scanner.ts` into a shared `extractTrackTags()` (`src/services/trackTags.ts`) so scan and upload apply identical fallback rules (missing title → filename, missing artist → "Unknown Artist") — the upload path passes the *original* client filename for this fallback, not the random staging name. Corrupt/unparseable files are rejected with `400` and the staged file is deleted (never filed into the library) — same music-metadata leniency as the scanner otherwise (e.g. a plain-text file renamed to `.mp3` doesn't always throw; that mirrors existing scan behavior, not a gap specific to upload).
- Filing (`src/services/trackFiling.ts`, new) computes `LIBRARY_PATH/<Artist>/<Album>/<filename>` — artist/album folder names sanitized (invalid filesystem characters replaced, trailing dots stripped, empty names fall back to "Unknown Artist"/"Unknown Album"), filename prefers the sanitized original upload name and falls back to the sanitized title only if that's empty. Never overwrites an existing file — same-name collisions get a `(2)`, `(3)`, ... suffix. Staged file is moved (not copied) into place via `fs.rename`, with an `EXDEV` (cross-filesystem) fallback to copy+delete so staging and the library directory don't have to share a mount.
- DB insert reuses the existing `upsertTrack()` (`src/db/library.ts`) unchanged — same idempotent insert/update-by-path logic as a rescan, so re-running `/library/scan` after an upload updates the same row rather than duplicating it. Response is `201 { track }` using the same lean shape as `GET /tracks` (new `getTrackSummaryById()` in `src/db/browse.ts`), so the client doesn't need a follow-up fetch to confirm what was added.

**Smart shuffle:** Built and manually verified end-to-end (see `.docs/features/smart-shuffle/planning.md`).
- Only the "avoid same artist back-to-back" shuffle needs the backend — plain shuffle/repeat-one/repeat-all are pure client-side queue operations with no server involvement (tracked as a follow-up for the Android playback plan, not built here).
- `smartShuffle()` (new `src/services/shuffle.ts`) — pure function, no DB/HTTP dependency: groups `{ trackId, artistId }` by artist, then greedily interleaves by always placing next from the largest remaining artist group that isn't the one just placed (the standard "reorganize string" algorithm). Guarantees zero adjacent same-artist pairs unless one artist exceeds half the set, in which case it hits the mathematical minimum (`2×dominant - total - 1`) rather than leaving it to chance. Input is pre-shuffled so both within-group order and equal-size-group tie-breaks vary between calls. `artist_id IS NULL` tracks are grouped together as their own bucket, not scattered as singletons.

## Resolved decisions

- **Backend:** custom Node.js/TypeScript build (Fastify) — Navidrome (fork or otherwise) is **not** being used. See `.docs/history/backend-decision-history.md`.
- **Database:** SQLite, own schema, FTS5 + WAL mode.
- **Auth:** JWT + bcrypt (backend) — implemented, see above; bearer token stored via encrypted DataStore (Android, not yet built).
- **Deployment target:** Docker, on the existing home server hardware.
- **Local dev environment:** WSL2 for backend, native Windows/Android Studio for the Android app.
- **Entry model (decided 2026-09-11, not yet built):** passwordless **guest entry** replaces the login form — an arcade-style title screen with one "click here to enter" button mints a randomised session token and a `kind = 'guest'` row. One identity per device, never a shared house account; a handoff link/QR moves an identity to a second device so cross-device resume survives. The password login stays for the owner at an unadvertised `/login`, because upload / scan / user management must not be reachable by whoever pressed the button. Plan: `.docs/features/guest-access-and-title-screen/planning.md`; reasoning: A13–A16 in `QUESTIONS.md`.
- **Web frontend scope:** full parity with — actually beyond — the Android app in *management* capability (Android stays the listening client; web is the control room). React + TypeScript + Vite + Tailwind + TanStack Query. Admin-role model (`is_admin`, CLI-bootstrapped) gates delete/hide/not-recommended/upload; browsing, preview playback, and the health dashboard stay open to any signed-in user. Full 4-phase plan (Plan/Structure/Interior/Walkthrough) done, see `.docs/features/library-management-interface/planning.md` — build not started.
