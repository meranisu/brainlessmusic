**Auth (JWT + bcrypt):** Built and manually verified end-to-end.
- `POST /auth/register` — accepts `{ username, password }`, hashes with bcrypt (12 salt rounds), inserts into `users`. Returns `201 { id, username, isAdmin }`; `409` on duplicate username, `400` on missing fields or a password under 8 characters / a username outside `[A-Za-z0-9._-]{2,32}`. **Gating is configurable as of 2026-09-09**: `ALLOW_OPEN_REGISTRATION` (default `true`) lets anyone create a listener account; `false` requires an admin's token. Either way the first account on an empty server is allowed through and becomes an admin. Self-serve accounts are never admins.
- `POST /auth/login` — verifies bcrypt hash, returns `200 { token }` (JWT, `sub`+`username` payload, expiry from `JWT_EXPIRES_IN` env, default `7d`) or `401` on bad credentials.
- `GET /auth/me` — protected via `fastify.authenticate` decorator (`src/plugins/auth.ts`); requires `Authorization: Bearer <token>`, returns `200 { id, username }` (never the password hash), `401` if the header is missing/malformed or the token is invalid/expired.
- JWT secret read from `.env`'s `JWT_SECRET`. Since 2026-09-09 the server **refuses to boot** if it is the default, empty, or under 32 characters, unless `NODE_ENV` is `development` or `test` (`utils/secretPolicy.ts`); `config.jwtSecret` still falls back to `'change-me'` so the CLI scripts keep working.

**Audio streaming:** Built and manually verified end-to-end.
- `GET /tracks/:id/stream` (`src/routes/tracks.ts`) — requires auth (`fastify.authenticate`); looks up the track by id, `fs.stat`s its stored path, and streams the file back with `Content-Type` set from file extension (`src/services/streaming.ts`: `.flac`→`audio/flac`, `.opus`→`audio/opus`, `.mp3`→`audio/mpeg`, `.m4a`→`audio/mp4`, `.ogg`→`audio/ogg`; unknown falls back to `application/octet-stream`).
- Byte-range support: parses a single `Range: bytes=...` header (start-end, open-ended, and suffix forms), responds `206` with `Content-Range`/`Content-Length`/`Accept-Ranges: bytes`; malformed or out-of-bounds ranges get `416` with `Content-Range: bytes */<size>`. No request-range header falls through to a full `200` response. Multipart (multi-range) requests aren't supported — treated as invalid.
- **Caching (2026-09-10):** the direct path sends a strong `ETag` (size + mtime), `Last-Modified`, and `Cache-Control: private, max-age=86400`, and answers `304` to `If-None-Match` / `If-Modified-Since` under RFC 9110 precedence — a tag decides alone, the date is consulted only in its absence and compared at whole seconds. `If-Range` is honoured: a range whose validator no longer matches is dropped and the whole file resent, since splicing new bytes onto old ones is a corrupt stream that arrives looking like a successful `206`. The tag is **strong** on purpose — a weak one may not validate an `If-Range`, which would have silently killed resumable seeking. A day rather than a week bounds how long a replaced file can keep serving the old rip; the media token in the URL rotates every two hours anyway, so a longer window buys little.
- ~~Transcoding (superseded 2026-09-10 by "Converted copies are cached" below — `?quality=low` is now a cached file, not a live encode):~~ `?quality=low` streams the file through `fluent-ffmpeg` on the fly (`libopus`, 64k target bitrate, ogg container, `Content-Type: audio/ogg`, `Accept-Ranges: none` — output length is unknown ahead of time so range serving doesn't apply to this path, and it sends `Cache-Control: no-store` for the same reason). `.noVideo()` is required on the ffmpeg command — without it, ffmpeg transcodes embedded cover-art image streams into a spurious Theora video track, bloating the output.
- **Converted copies are cached (2026-09-10):** `?quality=low` writes the conversion to disk and serves the file, so the data-saver path now has `Content-Length`, byte ranges, an `ETag`, `304`s and a working scrubber — it had none of those as a live encode. Measured on a 25s FLAC: 0.88s cold, 0.027s warm, 3.32 MB down to 0.24 MB (93%). Converting is skipped when the source is under 1.5x the 64k target. Raw `.aac` is remuxed to `.m4a` on every path, because ADTS reports a duration ~50% long to both ffprobe and Chrome. `TRANSCODE_PATH`, `TRANSCODE_CACHE_MAX_MB` (2048, LRU, evicted after a write), `TRANSCODE_MIN_SOURCE_BITRATE_RATIO`. The live-transcode path and its `?t=` offset were removed as unreachable once a finished file could be seeked by byte range.
- **Data saver is reachable (2026-09-10):** the web player has a toggle on both surfaces — a pill in the phone sheet beside shuffle and repeat, a button on the desktop bar. It applies to the track already playing rather than the next one, carrying the position, the play/pause state and the in-progress scrobble across the swap; that is only possible because the converted copy is a finished file that can be seeked. The preference is per-device (`localStorage`, key `brainlessmusic.dataSaver`), not per-account, since the phone on mobile data and the desktop on the LAN share a login and want different answers. Alongside it a readout shows **what was served, not what was asked for** — `variantFor` declines to downgrade a source already at or below the target, so those two come apart on exactly the files the rule protects. An `<audio>` element exposes no response headers, so this costs one `Range: bytes=0-0` request per track; on a cold cache it is nearly free, because the element is fetching the same variant and the in-flight map collapses them. Measured on the real library: 115 kbps Opus serves at 74 kbps, a 36% saving. **Known and not fixed:** the 64k target lands at 74.3 kbps because libopus default VBR overshoots — `-vbr constrained` measures 64.9 kbps on the same source. Filed as Q13; the cache key does not include the recipe, so a change there needs a variant-id bump.
- **Seven formats (2026-09-10):** the library accepts `.flac`, `.opus`, `.mp3`, `.m4a`, `.ogg`, `.wav` and `.aac`. All seven verified against real ffmpeg fixtures for tags, duration and waveform decode, and FLAC/WAV/AAC all confirmed playing in headless Chromium. **Raw `.aac` is a known trap:** frame-scanning gives the true duration but ffprobe and Chrome both estimate ~50% long from bitrate, so the seek bar lies — roadmap box 24 remuxes it to `.m4a`. `MAX_UPLOAD_SIZE_MB` was raised from 100 to **1024** the same day, since a single hi-res FLAC exceeds the old ceiling; the route is admin-only, the web client uploads 3 at a time (so staging can hold ~3× that), and a future reverse proxy needs its own body limit raised to match.
- **Seeking the data-saver path (2026-09-10) — SUPERSEDED the same day.** `?t=` was removed in `216aaf7`: once a converted copy is a finished file on disk, seeking is an ordinary byte range and the offset had no caller. The UI gap this entry named is closed too — see "Data saver is reachable" below. Kept for the record: `?t=<seconds>` started the transcode at an offset, applied as an ffmpeg *input* seek so it jumps rather than decodes-and-discards. Byte ranges still do not apply to a live encode — this is the way back into the middle of a track on that path. Invalid offsets are `400`, not clamped. Previously the ffmpeg handle was discarded, so a skipped track left ffmpeg blocked on a full pipe for the life of the server — one stranded process per skip. **Track upload:** Built and manually verified end-to-end.
- `POST /tracks/upload` (`src/routes/tracks.ts`, requires auth) — `multipart/form-data`, single `file` field, via `@fastify/multipart` (registered in `src/app.ts` with `limits.fileSize` from `MAX_UPLOAD_SIZE_MB`, default 100, and `limits.files: 1`).
- Extension allow-list is shared with the scanner (`AUDIO_EXTENSIONS` in the new `src/services/trackTags.ts`: `.flac`/`.opus`/`.mp3`/`.m4a`/`.ogg`) — unsupported extensions get `400` before anything is written to disk.
- The client-supplied filename is never trusted beyond its extension: the file is streamed to `UPLOAD_STAGING_PATH` (default `./data/upload-staging`, gitignored under `data/`) under a server-generated `crypto.randomUUID()` name. Oversized uploads (over the configured limit) are caught via `@fastify/multipart`'s `file.truncated` flag after streaming completes, the partial staged file is deleted, and the response is `413`.
- Tag extraction was pulled out of `src/services/scanner.ts` into a shared `extractTrackTags()` (`src/services/trackTags.ts`) so scan and upload apply identical fallback rules (missing title → filename, missing artist → "Unknown Artist") — the upload path passes the *original* client filename for this fallback, not the random staging name. Corrupt/unparseable files are rejected with `400` and the staged file is deleted (never filed into the library) — same music-metadata leniency as the scanner otherwise (e.g. a plain-text file renamed to `.mp3` doesn't always throw; that mirrors existing scan behavior, not a gap specific to upload).
- Filing (`src/services/trackFiling.ts`, new) computes `LIBRARY_PATH/<Artist>/<Album>/<filename>` — artist/album folder names sanitized (invalid filesystem characters replaced, trailing dots stripped, empty names fall back to "Unknown Artist"/"Unknown Album"), filename prefers the sanitized original upload name and falls back to the sanitized title only if that's empty. Never overwrites an existing file — same-name collisions get a `(2)`, `(3)`, ... suffix. Staged file is moved (not copied) into place via `fs.rename`, with an `EXDEV` (cross-filesystem) fallback to copy+delete so staging and the library directory don't have to share a mount.
- DB insert reuses the existing `upsertTrack()` (`src/db/library.ts`) unchanged — same idempotent insert/update-by-path logic as a rescan, so re-running `/library/scan` after an upload updates the same row rather than duplicating it. Response is `201 { track }` using the same lean shape as `GET /tracks` (new `getTrackSummaryById()` in `src/db/browse.ts`), so the client doesn't need a follow-up fetch to confirm what was added.
